## 三、当前 HLS 设计总览
### 3.1 顶层功能定义
当前 HLS 内核是单 attention kernel，顶层函数：
- `fpga/hls/fa_attention_kernel/fa_attention_kernel.cpp`

接口语义：
- 输入：`q / k / v`
- 输出：`o`
- 控制参数：
  - `seq_len`
  - `stride_bytes`
  - `scale_q8_8`
  - `neg_large_q8_8`
  - `causal_en`
- profile 输出：`profile`

HLS 顶层总线组织：
- `m_axi gmem0`: `q`
- `m_axi gmem1`: `k`
- `m_axi gmem2`: `v`
- `m_axi gmem3`: `o`
- `m_axi gmem4`: `profile`
- `s_axilite control`: 控制寄存器

### 3.2 当前支持的张量规模与排布
见 `fpga/common/fa_q8_8_attention.hpp`：
- `kMaxSeqLen = 256`
- `kHeadDim = 64`
- `kTileQ = 32`
- `kTileK = 64`
- `kRowPar = 2`
- `kSoftmaxCtxs = 4`
- `kQPairBatchRows = 8`

因此当前是一个：
- `D = 64`
- `S <= 256`
- `Q8.8` 数据表示
- causal/non-causal 均可
的单 head attention kernel。

## 四、输入输出数据流与架构组织
### 4.1 数据流主路径
当前 `run_attention_tiled_hls()` 的执行序列如下：
1. 从 `q` DDR 中搬运一个 `Q tile`
2. 初始化该 tile 的 softmax context：
   - `row_m`
   - `row_l`
   - `row_acc`
3. 采用 ping-pong 方式搬运 `K/V tile`
4. 对每个 `K/V tile`：
   - `generate_score_batch()` 生成 `ScorePacket`
   - `consume_score_batch()` 更新在线 softmax 上下文与 `row_acc`
5. 所有 `K/V tile` 完成后，对 `row_acc` 做归一化
6. 写回 `o`
7. 统计 profile 信息

### 4.2 结构分层
当前实现已经拆成接近 RTL 的 leaf 级别：
- `fa_q8_8_qk_dotprod_slice.cpp`
- `fa_q8_8_online_softmax_ctx.cpp`
- `fa_q8_8_o_normalize_block.cpp`
- `fa_q8_8_row_context_rf.cpp`
- `fa_q8_8_recip_nr_q16_16.cpp`
- 主调度：`fa_q8_8_attention.cpp`

### 4.3 当前 batch / ctx 组织形式
当前实现模仿 RTL 的核心想法：
- `ROW_PAR = 2`
- `SOFTMAX_CTXS = 4`
- 单批处理 `kQPairBatchRows = 8` 行
- 通过 `ScorePacket` stream 做 `score generate -> score consume`

这一步的意义是：
- 不是简单的逐行 attention
- 而是开始向 RTL 的“多上下文交错调度”靠近

## 五、任务分派规范与运行时接口
### 5.1 当前任务结构
运行时定义在：
- `fpga/integration/llama/fa_task_queue_runtime.hpp`

任务格式：

### 5.2 当前任务队列语义
当前 `AttentionTaskQueueRuntime` 支持：
- `submit()`
- `drain()`

注意：
- 现在的任务队列主要是**软件运行时层**的批量提交接口

### 5.3 运行模式
支持三种模式：
- `kSoftwareHls`
- `kStrictQ8_8`
- `kXrt`

当前板上最终目标是：
- `kXrt`

## 六、如何结合推理框架做高效处理
### 6.1 当前 llama.cpp 接入位置
后端位置：
- `inference/xcomp/llama.cpp/ggml/src/ggml-fpga/ggml-fpga.cpp`

当前只对接：
- `GGML_OP_FLASH_ATTN_EXT`

### 6.2 何时走 FPGA
当前只有满足以下条件时会走 FPGA：
- head dim 为 `64`
- `seq_len <= 256`
- `q_len == kv_len`
- `sinks == nullptr`
- `max_bias == 0`
- `logit_softcap == 0`
- 当前 attention 形状满足 HLS kernel 限制

不满足时回退 CPU。

### 6.3 为什么这样接入是高效的
这是当前最合理的做法，因为：
1. 直接挂在 `FLASH_ATTN_EXT` 这一层，不用改 tokenizer / sampling / server API
2. `llama-server` 可以继续对接现有评测脚本
3. 板上只需要额外准备：
   - `llama-server`
   - `libggml-fpga.so`
   - `xclbin`
   - 模型文件

## 七、内部设计细节：从算子到 ctx
### 7.1 dot-product
`qk_dotprod_slice_pair()` 是当前 attention 乘加主核之一。
它直接决定：
- score 生成吞吐
- DSP 消耗
- 上游 `generate_score_batch()` 的 II

### 7.2 online softmax ctx
`online_softmax_ctx_acc_row_step()` 维护：
- `row_m`
- `row_l`
- `row_acc`

这是当前 attention 正确性和吞吐的核心。
数值上它保证在线 softmax 累积；结构上它又是当前 HLS 最重要的时序与流水瓶颈之一。

### 7.3 normalize
`o_normalize_block_row()` 负责：
- `recip_nr_rtl_q16_16`
- `row_acc * recip`
- 最终 Q8.8 输出量化

这部分目前功能是对的，但总 latency 中占比不高，不是当前首要瓶颈。

## 八、HLS 综合结果总结
### 8.1 当前 HLS csynth 核心数据
来源：
- `docs/daily/archive/20260407_060500_hls_platform_summary_snapshot/hls/csynth.rpt`

当前 top 结果：
- Latency: `786727 cycles`
- BRAM: `165 (57%)`
- DSP: `353 (28%)`
- FF: `43372 (18%)`
- LUT: `43379 (37%)`
- Slack: `-3.11`

### 8.2 当前 HLS 关键子模块
- `qk_dotprod_slice_pair`
  - latency `16 cycles`
  - interval `4`
- `online_softmax_ctx_acc_row_step`
  - latency `8 cycles`
  - interval `8`
- `compute_kv_tile`
  - latency `18549 cycles`
- `init_row_context_rf`
  - latency `131 cycles`

### 8.3 当前 HLS 访存侧问题
`csynth.rpt` 已明确报出的关键问题：
1. `q` 读 burst 失败
   - 同一区域多潜在读导致 burst 不稳
2. `k/v` 读 burst 失败
   - `Stride is incompatible`
3. `o` 写 burst 失败
   - 同一区域多潜在写导致 burst 不稳
4. `profile` 写 widen 失败
   - 连续写长度不满足 widen 条件

这说明当前 HLS 延迟不只是 compute 问题，**访存组织也在明显拖累吞吐**。

## 十一、下一步优化方向
### 11.1 工程链路
1. 基于 `kv260_bist.xsa` 生成 `xpfm`
2. 使用 `fa_attention_kernel.xo` 运行 `v++ --link`
3. 生成 `fa_attention_kernel.xclbin`
4. 放入 `inference/ci/artifacts/kv260_upload_bundle/bitstreams/`

### 11.2 HLS 结构优化
优先级建议：
1. 优化 `q/k/v/o` 的 burst 条件，减少 `Stride is incompatible` 与 potential read/write 冲突
2. 继续压 `online_softmax_ctx_acc_row_step` 的 interval
3. 继续压 `qk_dotprod_slice_pair` 的 interval
4. 减少 `profile` 写 widen fail，避免无谓的 AXI 开销

### 11.3 与框架结合
- 保持当前 `FLASH_ATTN_EXT` 的后端接入方式
- 在 `xclbin` 出来后，优先打通：
  - `llama-server`
  - `sample.py`
  - `throughput_eval.py`
- 等 attention 板上稳定，再讨论更大范围的 GEMV/GEMM 复用与多任务调度
