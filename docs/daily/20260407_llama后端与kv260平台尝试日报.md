# 2026-04-07 `llama.cpp` 后端与 KV260 平台尝试日报

## 一、问题 1：`llama.cpp` 是否已经按 FlashAttention 算子接入后端

结论：**是的，已经接进去了。**

当前接入点在：

- [ggml-fpga.cpp](/3.2T/work/fpga-fa/inference/xcomp/llama.cpp/ggml/src/ggml-fpga/ggml-fpga.cpp)

具体是：

- 后端只接管 `GGML_OP_FLASH_ATTN_EXT`
- 通过 `ggml_fpga_supports_flash_attn()` 做形状/类型判定
- 真正提交任务的是 `ggml_fpga_compute_flash_attn()`
- 下层运行时走：
  - [fa_task_queue_runtime.hpp](/3.2T/work/fpga-fa/fpga/integration/llama/fa_task_queue_runtime.hpp)
  - [fa_task_queue_runtime.cpp](/3.2T/work/fpga-fa/fpga/integration/llama/fa_task_queue_runtime.cpp)

### 当前能命中的条件

- `D = 64`
- `seq_len <= 256`
- `q_len == kv_len`
- `FLASH_ATTN_EXT`
- `mask != nullptr` 时按 causal 口径
- `sinks == nullptr`
- `max_bias == 0`
- `logit_softcap == 0`

### 当前实现特性

- 若是 causal prefill，backend 会把 `seq_len` 向上补齐到 `kTileK=64` 的倍数
- 量化/提交在 backend 内完成
- 若不满足上述条件，会自动回退到 CPU 路径

这意味着：

- **短 prefill 的 FlashAttention 已经有 FPGA backend 接口**
- **decode 以及更一般的 attention 形状仍然不会命中 FPGA**

## 五、关于 `dtbo / shell.json / xclbin` 到底需不需要

这里要分两种运行方式：

### 1. 直接 `llama-server + XRT + xclbin`

如果：

- 板上已有匹配的 zocl/XRT 基础环境
- 平台生成的 XSA/XPFM 对应的 base shell 已经匹配

那么理论上最核心的是：

- `.xpfm`
- `fa_attention_kernel.xo`
- `v++ --link` 生成的 `fa_attention_kernel.xclbin`

即：

- **当前最优先缺的是 `xclbin`**

### 2. Kria app / `xmutil loadapp` 风格

如果要按教程那种：

- 拷到 `/lib/firmware/xilinx/<app>/`
- 走 `xmutil loadapp`

那就还需要：

- `.bin`
- `.dtbo`
- `shell.json`

所以：

- **教程截图里的 `pl.dtbo + shell.json + binary_container_1.bin` 是对应 Kria app 打包流**
- **我们当前 `llama-server + XRT` 路线，不一定非要先走到这一步**

但如果后面发现板端直接吃 `xclbin` 不够稳，那么回到 Kria app 打包流也是合理的备选。
