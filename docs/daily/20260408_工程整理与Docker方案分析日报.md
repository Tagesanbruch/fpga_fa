## x86 Docker 方案建议

### 目标

目标不是把 Xilinx 全家桶直接塞进 Docker，而是建立一个：

- 能在 x86 Linux 容器里统一运行开发和验证任务；
- 通过 git 拉取项目；
- 不依赖直接挂载当前工作目录；
- 可在准备好的 Linux 环境中打包复用的工作镜像。

### 用户场景与约束

当前目标用户是：

- Windows 主机用户；
- 需要使用 Windows 侧安装的 Vivado/Vitis；
- 同时希望有一个干净的 x86 Linux 开发环境来统一跑非 Xilinx 流程。

这里的核心现实约束是：

- Windows Docker Desktop + 挂载 Windows 目录 + 容器内直接接 Xilinx 工具链，这条路径通常不稳；
- Xilinx 工具对路径、权限、软链接、长路径、字符集、GUI/授权环境都比较敏感；
- 因此不建议把“Windows 本机 Xilinx 安装 + Docker 内直接调用”作为主方案。

### 建议方案

建议采用“两层环境”模式：

1. x86 Docker：统一承载开源工具和仓库任务
2. Windows/Linux 原生 Xilinx 环境：只负责 Vivado/Vitis/Vitis HLS

也就是说：

- Docker 负责：
  - RTL 仿真
  - cocotb
  - Verilator
  - CModel
  - llama.cpp
  - xcomp
  - Python/uv
  - 文档生成与报告归档
- Xilinx 环境负责：
  - HLS 综合
  - RTL kernel package
  - `v++ --link`
  - `xclbin`

### Docker 工作方式建议

不建议直接挂载当前目录。建议：

1. 创建一个独立 Ubuntu 镜像；
2. 容器启动后 `git clone` 仓库；
3. 通过 `.gitignore`/sparse/子模块策略，避免同步大文件和不必要的 third_party 副本；
4. 在容器内安装统一依赖；
5. 验证通过后将该镜像作为开发环境基线打包。

### Docker 内应支持的任务

第一版 Docker 建议覆盖：

- `uv` / Python 依赖管理
- `verilator`
- `cocotb`
- `pytest`
- `g++/clang`
- `cmake/ninja`
- `llama.cpp` x86 构建
- `xcomp` 路线所需依赖
- CModel 构建与运行
- 文档/报告脚本

第一版暂不覆盖：

- Yosys/STA
- 完整 Xilinx 工具链
- 板端 aarch64 交叉链的全自动镜像化

### Docker 目录和同步建议

建议 Docker 内部工程布局是：

- 单独 `git clone` 到容器内固定路径，比如 `/workspace/fpga-fa`
- 不同步：
  - `.Xil`
  - `.ipcache`
  - `third_party/kria-vitis-platforms/` 全量副本
  - 各类 `v++/vitis_hls` 日志
  - 大模型文件
  - 板端 bundle 中的大体积二进制
- 可保留：
  - RTL/HLS/runner/bundle 脚本
  - docs/daily
  - 轻量报告文本
